# FlowKit Controller Protocol

This protocol is shared by the eight direct Codex skills. The installed workflow definition is the source of prompts, commands, branches, and gates. Never copy those decisions into a skill or invoke `specify workflow run`.

## Preflight

1. Confirm the selected task is in the consumer project and the requested skill ID maps to the requested workflow ID in the installed `manifest.yml` and `skills-install.json`. Stop if either record is absent, incompatible, or inconsistent.
2. Gather the required workflow values from the invocation or ask for missing values in the main task. Pass each value as `--input name=value` to `bash .specify/flow-kit/scripts/bootstrap.sh "$PWD" <workflow-id> <skill-id>`. The bootstrap locates and version-checks the active Specify runtime, loads the composed installed workflow read-only, and returns its graph, resolved inputs, and digest. Never run it from the FlowKit source checkout on behalf of another consumer.
3. Read the JSON graph and resolved inputs. The helper applies declared defaults, rejects missing or blank required values and unknown input keys, and never prints the supplied values in an error message.
4. Check the graph and all switch branches. Step IDs must be unique; only `prompt` and `command` nodes may declare a concrete model and optional `reasoning_effort`. Reject unknown node types, malformed model or effort values, unsupported template forms in any branch, workflow-level model defaults, and unsupported command integrations before starting a step. Resolve prior-step output values only when the referenced step has completed.
5. Apply a supplied `step_id`, `model`, and/or `reasoning_effort` override to exactly one modeled step. Do not infer an override. Resolve omitted effort to `medium`. Show the operator all effective model-effort pairs, including untaken branches.
6. Before workflow work, probe every distinct model-effort pair with a bounded child using that exact model and effort. The probe must only return an availability token; it must not inspect or edit the project, invoke skills, or call tools. Wait for every probe, then use a new child for each modeled workflow node; never send workflow work as a follow-up to a probe child. If a child cannot be started, fails, or returns anything other than its expected token, stop without a run record or workflow state change. Never substitute another model or effort.
7. Capture the starting workflow digest and content/device/inode fingerprints for `.specify/bundle-records.json` and `.specify/flow-kit/skills-install.json`. Create the compact run summary only after preflight succeeds.

## Execute the Installed Graph

Process nodes in order. Keep the run's current node, outputs, completed node IDs, child task IDs, and starting fingerprints in the main task context and summary. Before every new node, re-read the installed definition and compare its digest and both install-record fingerprints. After a child returns, compare them again. If any value changed, let that active node finish, record the stop, and do not start another node. A changed skill package is a refresh even if workflow YAML stayed the same.

- **Prompt node**: Render only `{{ inputs.name }}` and `{{ steps.id.output.path }}` references from available inputs and prior outputs. Stop on an unresolved or unsupported expression. If modeled, start one child with the effective model and effort and the rendered prompt; otherwise perform the prompt in the main task. Capture a concise result for later references. Preserve edits if the node fails.
- **Command node**: Render its integration and YAML argument string. Only `codex` is supported. Resolve a project-installed command skill using the pinned naming rule (replace dots with hyphens), then verify its `SKILL.md` name and available ownership provenance. Invoke that skill with the rendered arguments in the main task for an unmodeled node or in one bounded child using the declared assignment for a modeled node. Tell a modeled child explicitly that it is executing only this command node, give it the installed command skill ID and rendered arguments, and require it to return its result to the parent. The child must not invoke a `flow-kit-*` skill, bootstrap a workflow, create a FlowKit run summary, own a workflow gate, or dispatch another child to re-run this command node. The main task alone owns those controller actions. Never call native workflow execution or substitute a global skill, copied prompt, or similarly named command.
- **Gate node**: Present the installed `message` and `options` to the human in the main task, with numbered choices and a custom response only when the workflow allows it. Wait for the human's explicit choice. Pass the gate node and raw answer as JSON on stdin to `python3 .specify/flow-kit/scripts/python/controller.py gate`; use only its validated `choice` as the gate output. A missing or invalid choice stops at the gate.
- **Switch node**: Evaluate its installed expression from inputs and captured step outputs. Pass the switch node and resolved choice as JSON on stdin to `python3 .specify/flow-kit/scripts/python/controller.py branch`; follow only its returned `steps`. Stop if the expression cannot be resolved. Never execute more than the selected branch.

When a child needs a human answer, it must return one structured request with `kind: question`, its `step_id`, question text, options, and whether a custom answer is allowed. Options may be short strings or objects with `id` and `description`; object descriptions are display text and answers resolve to their IDs. Pause that child; the current workflow node remains active through the answer relay. Validate the request by passing its JSON on stdin to `python3 .specify/flow-kit/scripts/python/controller.py question --step-id <active-step-id>`; the helper normalizes `allow_custom`, `custom_allowed`, or `allow_custom_answer` to `allow_custom_answer` and rejects conflicting flags. Present the validated options in the main task as numbered choices plus a custom-answer option when allowed. After the human responds, pass `{"request": <validated-request>, "answer": <raw-human-answer>}` on stdin to `controller.py answer --child-id <original-child-id> --target-child-id <follow-up-target-id>`. Send only the validated answer as a follow-up to that same child task ID and wait for its continuation. Compare the starting fingerprints after continuation before any later node. Do not create a replacement child or answer on the human's behalf. If validation or continuation fails, stop and preserve its partial work. Do not put the raw question or answer in the recovery summary.

Questions and gate decisions must stay in the main task. Completing one workflow never authorizes another phase, roadmap verification, Git integration, publication, merge, or feature acceptance.

## Recovery and Stop Rules

Use `.specify/flow-controllers/runs/<run-id>/summary.json` only after successful preflight. Create it by piping JSON containing `workflow`, `fingerprints`, `assignments`, and `preflight_passed: true` to `python3 .specify/flow-kit/scripts/python/recovery.py create --project "$PWD"`. Update it atomically before each child dispatch and after every step boundary by piping `{"changed_files": ["relative/path"]}` to `recovery.py step --summary <summary-path> --step-id <id> --status <pending|running|waiting_for_human|completed|incomplete>`. Use only a bounded blocker code: `child-unavailable`, `command-unavailable`, `human-input-missing`, `human-relay-failed`, `installation-changed`, `main-task-interrupted`, `operator-deferred`, `preflight-failed`, `step-failed`, `unsupported-workflow`, `unspecified-stop`, or `workflow-changed`. Pass that code in a step update or to `recovery.py stop --summary <summary-path> --blocker <code>` for a run-level stop; use `recovery.py interrupt --summary <summary-path>` after interruption. Explain the specific reason in the main task without placing child transcripts, secrets, absolute paths, or file contents in the record. Record the workflow ID, version, digest, starting install fingerprints, effective step assignments, step statuses, repository-relative changed paths, and blocker code. A running step found after interruption becomes incomplete. Never auto-resume, retry, roll back partial edits, or start a later workflow. Report the summary path and stop reason in the main task.

If a runtime, workflow, input, command skill, model-effort pair, child dispatch, human relay, or installation ownership check is missing or uncertain, stop at the smallest affected boundary. A preflight rejection creates no run summary or native workflow run state.
