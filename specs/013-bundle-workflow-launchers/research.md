# Research: Codex Workflow Controllers

The findings below are based on the pinned Specify CLI `1.0.10.dev0+pegagio.2`, current FlowKit source, and the desktop child-task capability available during planning. They define implementation gates; they are not a claim that the complete controller already works.

## Decision: Put concrete models on individual executable steps

Specify accepts a string `model` on `prompt` and `command` steps, and its Codex integration passes that string to a separate `codex exec --model` invocation. An in-memory validation of `model: gpt-6-sol` passed. The same validator also accepted `model: ''` and does not verify account access. The controller will therefore require a nonempty concrete ID on each modeled executable step and reject a declaration on a gate, switch, or unsupported step type. All eight current workflow files lack model declarations, so their source changes and version bumps are part of implementation. (Installed Specify `workflows/steps/prompt/__init__.py`, `workflows/steps/command/__init__.py`, `workflows/engine.py`; `workflows/speckit-flow-*/workflow.yml`.)

**Rationale**: A step-level field matches FR-006 and permits distinct reviewed choices and a single named-step override. Do not set `workflow.model` in this feature: its inheritance would make an unmodeled step implicitly modeled and blur the main-task/subagent boundary. The initial assignment matrix is in [plan.md](plan.md#reviewed-step-model-assignments): `gpt-6-sol` covers most modeled steps and all `return-to-*` commands, `gpt-6-luna` with high effort runs implementation and task generation, and `gpt-6-astra` with medium effort handles the primary planning, artifact analysis, and convergence assessments. These are concrete reviewed defaults for this feature, not portable model roles; review the complete assignment diff before release.

The tested Specify loader preserves an unknown `reasoning_effort` key on a command step and its validator accepts the definition, but its native step executor reads only `model` for Codex dispatch. FlowKit must treat an omitted effort on a modeled step as `medium`, read a step-level `reasoning_effort` override, validate the model-effort pair, and pass both to the Codex child. The two Luna steps declare `reasoning_effort: high`; no workflow-level effort field is used. Native `specify workflow run` does not honor this FlowKit metadata, so documentation and manual fallback must not promise identical effort outside the controller. (Installed Specify `workflows/engine.py`, `workflows/steps/command/__init__.py`; read-only in-memory validation of the current implementation workflow.)

**Alternatives considered**: A consumer model-role mapping is a later feature. A global workflow model or skill-local mapping would obscure the step source of truth. Native `specify workflow run` passes models to separate CLI sessions and loses the selected desktop task experience.

## Decision: Interpret the installed, composed definition in the desktop task

`WorkflowEngine(project_root).load_workflow(id)` composes the installed workflow with overlays without dispatch. `specify workflow resolve` reports provenance, not the full execution graph. `WorkflowEngine.execute` writes run state before execution and invokes the CLI Codex integration, so the controller must not call it. The current eight workflows use ordered `prompt`, `command`, `gate`, and `switch` nodes. A shared controller helper will load and validate the composed definition, enumerate every branch for preflight, and expose the next node and rendered inputs. The main task executes unmodeled nodes and gates and dispatches modeled prompt/command nodes to bounded children. Unsupported node types or unresolved template expressions stop the run. (Installed Specify `workflows/engine.py`; `workflows/speckit-flow-*/workflow.yml`.)

**Rationale**: This uses versioned installed YAML for prompts, gates, and branch decisions without copying them into eight skills. Conformance checks against the pinned Specify interpretation are required for all eight graphs, including nested switch branches.

**Alternatives considered**: Eight handwritten controller flows would duplicate governing logic. Modifying the Specify engine to provide a desktop dispatcher would couple this feature to a broader CLI change. Native dispatch remains available as the manual/CLI path.

## Decision: Bridge to the selected Specify runtime

The configured skill-tools Python does not import `specify_cli` in the current checkout, while the installed `specify` command uses a separate Python environment. A Codex skill cannot assume that its ordinary Python process can call `WorkflowEngine.load_workflow`. Use a portable shell bootstrap that locates and version-checks the selected `specify` executable and runs the controller's read-only composition call with its compatible interpreter. Return only the composed graph and provenance to the main task. The controller must not dispatch a workflow or write run state, and unresolved executable or interpreter selection blocks preflight. Validate both a mise-selected and an ordinary executable in disposable consumers; use skill-tools Python for maintainer tests rather than requiring it in consumers. (Current `specify` executable shebang and `python3`/skill-tools import probes; installed Specify `workflows/engine.py`.)

**Rationale**: This keeps the existing Specify composition semantics without making the maintainer's private skill-tools environment a consumer dependency, installing Specify's dependencies into it, or copying the workflow parser into FlowKit. Runtime discovery must be explicit because the selected consumer task may use a different shell environment than the source checkout.

**Alternatives considered**: `specify workflow resolve` reports layer attribution but does not expose the composed execution graph. Calling `specify workflow run` would create separate CLI agent sessions and native run state. Importing `specify_cli` from ordinary or skill-tools Python fails in the tested checkout.

## Decision: Resolve workflow commands to installed Codex skills

The eight workflow graphs contain `command` nodes with IDs such as `speckit.tasks` and `speckit.flow-wiki.ingest`. In the selected Codex skills-mode consumer, Specify provides corresponding skills such as `speckit-tasks` and `speckit-flow-wiki-ingest`. The controller must use the pinned Specify command-to-skill mapping and inspect the selected project's installed skill inventory before executing a command node. The rendered workflow arguments accompany the invocation; the controller does not copy or reinterpret the command's underlying prompt. Verify the installed skill's declared name and source attribution where available. A missing or mismatched skill stops at that node; live validation must show a modeled child can reach the skill in the same project. (Current workflow YAML and `.agents/skills` inventory; installed Specify skill naming path.)

**Rationale**: The installed YAML chooses the command and arguments, while the installed skill owns command behavior. Checking the selected project's inventory keeps the controller from silently using a global or stale skill with the same name.

**Alternatives considered**: Copying command prompt bodies into the controller would duplicate behavior. Native `specify workflow run` would leave the desktop task. Invoking an unchecked skill name could run an unrelated consumer skill.

## Decision: Deliver controllers as direct Codex skills

The current Specify bundle manifest supports extensions, presets, steps, and workflows, but no direct skill component. Its extension command validator requires `speckit.{extension}.{command}`, and its skill generator forces a `speckit-` name. These controllers are Codex-facing orchestration, not new Specify commands. Keep eight reviewed `flow-kit-*` skill directories with `SKILL.md` and `agents/openai.yaml` in a versioned controller package. The supported FlowKit catalog route installs that package alongside the existing Specify bundle and records both in one release; a native `specify bundle` command alone installs only its declared Specify components. (Installed Specify `bundler/models/manifest.py`, `extensions/__init__.py`; `bundles/spec-kit-flow/bundle.yml`; `tools/catalog.py`.)

**Rationale**: Direct skill source gives the requested Codex IDs without inventing Specify commands or changing Specify's global naming rules. The FlowKit catalog route already wraps bundle installation; its release metadata and a local ownership record can bind the skill package to the reviewed workflow versions. One shared protocol limits drift across eight skills.

**Alternatives considered**: A controller extension would require unrelated Specify command IDs and a generator change to escape its forced `speckit-` prefix. `provides.skills` is unsupported by the pinned bundle schema. A preset is meant for command layering and introduces command-precedence coupling. A separate manual skill installation would lose the one-command FlowKit lifecycle and version alignment.

The current catalog installer refuses snapshot releases. The supported release commands retain that refusal; an explicit development-snapshot mode for install and refresh in disposable initialized consumers is needed to exercise the real catalog lifecycle and a skill-only mid-run refresh before publication. Snapshot packaging may use the current uncommitted feature files if it records exact source digests and dirty working-tree status without inventing a release commit or tag. Its output must identify the snapshot and may not be used as evidence of a released or adopted bundle.

## Decision: Preflight all model-effort pairs with a live, non-workflow child probe

The desktop child-task tool allows explicit model and reasoning-effort overrides when spawning with no or limited forked history; full-history forks inherit the parent model. The main task can continue the same named child with `followup_task` after it relays a human answer. A prior desktop probe showed child visibility and no direct composer, but it did not establish complete workflow dispatch. No side-effect-free account entitlement check was found; model catalogs and Specify schema acceptance are insufficient. Before changing workflow state, the controller will show the effective model-effort pair of every modeled step in every branch, apply overrides to at most one named step, and probe each distinct effective pair with a bounded child that performs no project work. Any rejected or inconclusive probe stops the workflow. A later dispatch failure also stops without fallback. (Current desktop child-task tool schema and prior interaction probe.)

**Rationale**: The probe tests model-effort availability in the selected task and account before workflow work, including untaken branches. It adds visible child tasks and cannot guarantee that access remains unchanged later; the controller must still fail closed at dispatch.

**Alternatives considered**: `codex debug models` lists catalog metadata but does not certify account access. Merely validating the YAML string would repeat the unsupported-model failure encountered with CLI dispatch. The [Responses multi-agent guide](https://developers.openai.com/api/docs/guides/responses-multi-agent) describes a different API surface whose children share the request model; it is not evidence for heterogeneous desktop children.

## Decision: Keep human turns and stopped-run evidence in the main task

A child needing input returns a structured question and pauses. The main task presents its options, receives the operator's answer, and resumes that same child. Gates are handled only in the main task. A rejected preflight reports the blocker without a run record. Initialize a compact consumer-local record after successful preflight and update it atomically at every step boundary so interruption leaves completed-step evidence. Record workflow ID/version/source digest, effective model-effort pairs, per-step status, repository-relative changed files, and blocker; preserve partial edits and never auto-retry or auto-resume. Compare the installed workflow identity before each new step and after an active child completes. If a refresh changed it, finish the active step, record the stop, and require a new invocation. (Feature 013 spec FR-009, FR-016–FR-019.)

**Rationale**: The tested child UI had no direct human composer, and partial edits are valuable recovery evidence. The pinned Specify CLI rewrites `.specify/bundle-records.json` on bundle install, refresh, and removal. The FlowKit catalog route must also atomically replace its skill ownership record on install, refresh, and removal. Compare content-and-file-identity fingerprints of both records as well as the composed workflow digest at each step boundary; a skill-only refresh can leave workflow bytes unchanged. An unrelated bundle operation can trigger a conservative stop, which is preferable to silently continuing through an uncertain refresh.

**Alternatives considered**: Child-side human interaction, automatic rollback, checkpoint replay, and transcript persistence conflict with the clarified behavior or add unapproved scope.

## Decision: Make skill ownership safety a release gate

The supported FlowKit catalog route must preflight skill names and content ownership before install, refresh, or removal, report conflicts without replacing or deleting consumer content, and verify actual controller inventory afterward. Record the installed package version and file digests in a local FlowKit ownership record. A native `specify bundle` operation has no skill lifecycle for this package and must not be documented as installing or removing controllers. (Current `tools/catalog.py`; installed Specify `bundler/models/manifest.py`; `tests/test_bundle_lifecycle.py`.)

**Rationale**: A package ownership record alone does not prove an edited skill is still safe to delete. The feature cannot meet FR-011/FR-012 through an optimistic packaging claim.

**Alternatives considered**: Silently skipping a collision, force-overwriting a local skill, or deleting a modified skill on removal would violate the feature contract. If the supported catalog route cannot meet the contract, FR-015 requires an explicit operator decision before shipping.
